A model too big for the card has no single best split — it has one per question, and this is the question. Auto prices both plans at the context above and takes the one it predicts faster.

what each one gives up Ceiling keeps every block’s attention and KV on the GPU and exiles every dense FFN to RAM (-ngl all + -ot): nothing is left to pay with, so the context becomes whatever still fits. Fit holds the window you typed above and walks -ot down first — then -ngl if the full exile is not enough — paying in the least that fits.

The choice also decides what “best” means among the recorded measurements: the recommendation at the top of the results takes the largest context that loaded in the ceiling plan, and the least exile (FFN first, then layers) that loaded in the fit plan — not the fastest row. Decode re-reads the KV for the tokens present rather than the window allocated, so tok/s barely moves across contexts and ranking by it ranks noise.

A model that fits whole, and an MoE — whose --n-cpu-moe has one answer — have no such choice, and this is ignored for them.

Smaller quant, smaller cache. Anything below f16 needs flash attention, which Tune switches on for you.

Tunebatch, sequences

LM Studio calls these Physical Batch Size and Max Concurrent Predictions (its default is 4).

what seqs changes It sizes the recurrent state on hybrid models and the sliding-window cache on SWA models (Gemma, Mistral, gpt-oss) — llama.cpp allocates one window per sequence slot, so four slots is four windows.

Required for a quantized KV cache.

Text decoding runs at the same speed either way, so system RAM gives those megabytes back to the layers without giving up images — images themselves encode slower.

why this is a choice and not a measurement The campaign used to sweep this placement. It is not really a speed question: the projector only runs while an image is being encoded, and the VRAM it holds the rest of the time is what the split has to work around. Say where it goes and the plan and the measurement both use that.

×

Leave this ticked on CUDA. It matters more than the image size does. Derived, not measured — unlike everything else here.

why the tick box beats the image size The projector's weights are charged above. This reserves what the encoder needs while it runs. Unfused, that is quadratic in pixels — attention is n_head × n_patches², so a 2560×1600 screenshot at 16px patches is 16,000 patches and several GiB, and halving each side cuts it ~4×. Fused, the quadratic term vanishes.

On CUDA, clip.cpp resolves CLIP_FLASH_ATTN_TYPE_AUTO by probing the backend, and the SigLIP tower these models share (head dim 72) is a supported size — just not on the tensor-core path. Untick it for a backend without a working FA path, to see the ceiling. Either way this is a default, not a measurement: your load log's flash attention is enabled/disabled line settles it. Note LM Studio's own Flash Attention toggle applies to the language model, not the tower.

SPECULATIVE DECODING

On by default in LM Studio for models that ship these blocks.

what it costs This model ships multi-token-prediction blocks. LM Studio turns this on by default for them (Speculative Decoding: MTP, llama.cpp --spec-type draft-mtp). It gives the draft blocks a KV cache back — at f16 regardless of your KV quant — plus a per-sequence slot. Untick only if you set Speculative Decoding to Off.

A dflash-*.gguf drafts as DFlash; a model file with MTP blocks (a *-MTP-*.gguf) drafts the target with its own multi-token prediction, like -md <file> --spec-type draft-mtp. Anything else is refused rather than guessed. Or type a path to a drafter file

Expertbudgets, overrides, calibration

VERIFY A CONFIG YOU RAN

Enter LM Studio’s “GPU Offload” number to price that exact config.

read the real value, not the slider Check the real value in the log (%APPDATA%\LM Studio\logs\main.log, “Resolved GPU config options”) — LM Studio silently adjusts the slider to respect its VRAM cap, so the number you set is not always the number it ran.

LM Studio’s “Number of layers to keep experts on CPU” / llama.cpp --n-cpu-moe. Not the GPU Offload slider: it moves only the routed experts of the first N blocks, leaving their attention and KV on the GPU.

llama.cpp -ot: the first N blocks’ dense FFN tensors (gate/up/down) move to the CPU while their attention and KV stay on the GPU. Blank lets the plan mode choose — both modes pin every block. A number prices the exact split you ran instead.

BUDGETS

RAM budget defaults to total installed, since a model can load into standby/paged memory. The header shows what is free now; the plan warns if it exceeds that.

Headroom on top of the plan, and the basis a speed campaign is seeded with.

what is already accounted for The CUDA context and driver overhead are already inside the compute-buffer estimate - they were fitted together against measured loads - so the reserve is for something else wanting the card, e.g. your desktop. It defaults to 512 MiB because that is what the speed sweep plans against, and the two disagreeing by any amount moves the recommended split.

SPEED MODEL

KV is re-read every token, so speed depends on how full the context actually is — not on the size you allocated. RAM efficiency is set by Calibrate.

COMPUTE BUFFER

Weights and KV are exact; the compute buffer is the one estimated term. With a model loaded right now, Measure reads the engine’s real VRAM and back-solves the true overhead — no load log needed.
